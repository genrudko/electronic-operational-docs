# Электронная оперативная документация

Независимый демонстрационный прототип модульной системы для оперативного персонала.

## Локальный запуск без Docker

```powershell
Set-Location "G:\electronic-operational-docs"
.\scripts\run_dev.ps1
```

Скрипт использует постоянный локальный порт `8765`. Поэтому адреса можно сохранить
в закладках браузера:

```text
Главная страница: http://127.0.0.1:8765/
Проверка состояния: http://127.0.0.1:8765/health/
```

Проверить кодировку, доступность порта и адреса без запуска Django:

```powershell
.\scripts\run_dev.ps1 -CheckOnly
```

Если порт `8765` занят, скрипт завершится с понятной ошибкой и не станет молча
переходить на случайный адрес. Для разового ручного запуска на другом порту:

```powershell
.\scripts\run_dev.ps1 -Port 8766
```

## Демонстрационные персональные записи

Вымышленные локальные записи:

```text
operator.demo   / EodDemo!2026
supervisor.demo / EodDemo!2026
```

Они предназначены только для локального прототипа. Каждая учётная запись связана ровно с одним сотрудником.

Повторное заполнение организационного справочника:

```powershell
.\.venv\Scripts\python.exe manage.py seed_demo_organization --reset-passwords
```

## PostgreSQL-профиль

PostgreSQL остаётся целевой базой проекта. При наличии Docker:

```powershell
.\scripts\run_postgres.ps1
```

SQLite используется для локального интерфейсного прототипирования и проверки доменных инвариантов.
Полноценная проверка параллельной регистрации и блокировки серверного нумератора выполняется
на PostgreSQL отдельным `TransactionTestCase`.

## Patch 004: системное подтверждение и целостность

Пользовательская регистрация теперь выполняется через предварительный просмотр и повторный
ввод текущего пароля. После успешной проверки в одной транзакции создаются регистрационный номер,
неизменяемый канонический снимок, SHA-256, системное подтверждение и аудит.

Статусы проверки:

- `VALID` — снимок, подтверждение и текущее зарегистрированное содержимое согласованы;
- `INVALID` — обнаружено расхождение или повреждение;
- `LEGACY` — документ существовал до Patch 004 и перенесён без повторной аутентификации;
- `MISSING` — обязательный снимок или подтверждение отсутствует.

`PASSWORD_REAUTH`, `DEMO_SEED` и `LEGACY_MIGRATION` всегда различаются. Пароль не сохраняется.
Механизм является функцией демонстрационного прототипа и не объявляется УКЭП или УНЭП.
Он обнаруживает расхождения данных, но без внешнего ключа/якоря не противостоит администратору БД,
который может одновременно изменить записи и пересчитать контрольные суммы.

## Patch 005: нормативный реестр и контекстная справка

Добавлен нормативный реестр с редакциями, требованиями и трассировкой
`требование → функция → тест → приёмочный сценарий`. Опубликованные редакции
неизменяемы и имеют SHA-256.

История наименований и конфигурация организации хранятся отдельными
публикуемыми редакциями. Пользовательский интерфейс показывает русские
наименования системных статусов и контекстную справку по техническим полям.
## Patch 005.1–006: реестр оборудования и управляемая справка

Контекстные подсказки больше не перекрывают друг друга: одновременно открывается
только одна карточка, предусмотрены закрытие кликом вне подсказки, клавиша Escape,
позиционирование в границах экрана и мобильная нижняя карточка.

Добавлен реестр энергообъектов и оборудования с иерархией, видами КТП, ВЭУ, РУ,
ПС, линий, РЗА и СДТУ, связями, алиасами и неизменяемыми редакциями диспетчерских
наименований. При регистрации документа создаётся исторический снимок выбранного
оборудования. Новые документы используют канонический снимок
`eod.document.registration.v2`, а документы Patch 004 версии 1 продолжают проверяться.

## Patch 006.1: масштабируемый селектор оборудования

Длинный `select multiple` заменён серверным селектором. Поиск выполняется порциями
по 50 записей с фильтрами по энергообъекту, категории и виду оборудования.
Выбор сохраняется при поиске и смене страниц, а форма принимает только оборудование
организации текущего пользователя.

## Patch 006.2: защита репозитория и очищенная история

Репозиторий принудительно проверяется как закрытый. Реальные инструкции, офисные
документы, PDF, архивы, экспорты чатов и полные внешние планы не являются частью
кодовой базы.

История очищена от ранее ошибочно добавленных материалов. `git_finalize_patch.py`
теперь проверяет allowlist для всех staged-путей, включая уже отслеживаемые файлы,
и блокирует commit/push, если GitHub-репозиторий не имеет видимость `private`.

После переписывания истории старые клоны использовать для push нельзя. Рабочий
клон, на котором выполнен Patch 006.2, уже синхронизирован с новой историей.

## Patch 007: управление и ведение

Добавлен самостоятельный реестр диспетчерского управления и ведения режима.
Управление и ведение разделены, информационное ведение является характеристикой
ведения, а субъекты и уровни выбираются из формальных справочников.

Опубликованные редакции фиксируют срок действия, документ-основание, автора,
серверное время и SHA-256. Для одного оборудования на одном уровне запрещены
пересекающиеся активные управления. Взаимодействие смежных субъектов задаётся
явно и также публикуется редакциями.## Patch 007.2: презентационный интерфейс

Пользовательские страницы управления и ведения переведены на смысловые карточки.
Коды, номера редакций, SHA-256 и диагностика скрыты по умолчанию и включаются в
персональных настройках учётной записи. Добавлены тема, плотность, размер текста,
ширина рабочей области и локальная система SVG-иконок.

Демонстрационный профиль использует узнаваемое публичное название
«Кочубеевская ВЭС» и естественные вымышленные ФИО. Он не содержит фактических
персональных данных работников, реального оперативного распределения, внутренних
номеров документов или иных производственных сведений.## Patch 007.3 — тема, терминология и презентационная база

Пользовательские экраны различают диспетчерское и технологическое управление
и ведение. Информационное ведение хранится как характеристика ведения.
Светлая и тёмная темы используют общие семантические поверхности.

Локальный сервер по умолчанию работает с `data/presentation.sqlite3`.
Gate-проверки и патчи должны использовать отдельный `SQLITE_PATH`, чтобы
контрольные документы не попадали в презентационный профиль.

Автоматический push отключён. Патчи создают локальные commits.

## Patch 007.4 — организационная структура и профиль запуска

- Добавлена структура ЦОТУиЭ ВЭС Невинномысск и отдельный участок ТОиР лопастей ВЭУ.
- Организационная принадлежность отделена от обслуживания энергообъектов.
- Кочубеевская ВЭС, Кузьминская ВЭС и ПС 330 кВ Барсуки учитываются как энергообъекты.
- Общий оперативный персонал имеет явные допуски ко всем трём объектам.
- Оперативная подчинённость участка задана отдельно от административного дерева.
- Локальный запуск защищён от устаревшего `SQLITE_PATH` и использует `presentation.sqlite3`.
- Реальные персональные данные не используются; автоматический push отключён.
