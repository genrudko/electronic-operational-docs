# AGENTS.md — обязательный контракт AI-разработчика ЭОД

Этот файл обязателен для любого AI-ассистента, агента или нового чата, работающего с репозиторием.

## 1. Перед началом работы

Сначала прочитать:

1. `README.md`;
2. `docs/INDEX.md`;
3. `docs/project/CURRENT_STATE.md`;
4. `docs/project/CURRENT_HANDOFF.md`;
5. `docs/project/DOMAIN_INVARIANTS.md`;
6. `docs/process/PROJECT_OPERATING_SYSTEM.md`;
7. `docs/process/DEVELOPMENT_WORKFLOW.md`;
8. профильный ADR и runbook для затрагиваемого контура.

Не восстанавливать состояние проекта по памяти, названию ветки или одному сообщению чата.

## 2. Роли

Пользователь:

- владелец продукта и предметный эксперт энергетики;
- не обязан читать, писать или исправлять код;
- формулирует цель и проверяет предметную корректность, UX и сценарии;
- единственный разрешает merge принятого результата в `main`.

AI-разработчик:

- самостоятельно исследует репозиторий и источники;
- проектирует полное изменение;
- создаёт код, миграции, тесты, документацию, commits и PR;
- анализирует CI, VPS-логи и результаты приёмки;
- не перекладывает программирование на пользователя.

## 3. Рабочая модель

Основной цикл — GitHub-first и VPS-first:

1. создать или использовать отдельную рабочую ветку;
2. реализовать изменения непосредственно в GitHub;
3. получить зелёный CI;
4. обновить `/srv/eod/development` через `git pull --ff-only`;
5. выполнить refresh/rebuild, checks, tests и status;
6. предоставить пользователю маршрут предметной и визуальной приёмки;
7. исправить подтверждённые дефекты в той же ветке;
8. merge выполнять только после явной команды пользователя;
9. после merge синхронизировать preview и зафиксировать новый baseline.

Скачиваемые автономные patch-файлы являются аварийным fallback, а не нормальным процессом.

## 4. Инфраструктурные инварианты

- accepted preview: `/srv/eod/repository`, только `main`, Compose project `eod-preview`, база `eod_preview`, порт `127.0.0.1:8765`;
- active development: `/srv/eod/development`, никогда не `main`, Compose project `eod-development`, база `eod_development`, порт `127.0.0.1:8766`;
- PostgreSQL не публикуется на host port;
- секреты preview и development не смешиваются;
- VPS deploy key остаётся read-only;
- код не редактируется непосредственно в preview checkout;
- development-база может получать копию accepted preview, но reset не имеет права записывать в preview.

## 5. Предметные инварианты

Обязателен полный документ `docs/project/DOMAIN_INVARIANTS.md`. Ключевые правила:

- интерфейс для конечного пользователя только русский;
- внутренние технические идентификаторы — профессиональный английский;
- оперативный журнал остаётся специализированным модулем;
- остальные журналы строятся на общем ядре, но рабочие формы определяются утверждёнными источниками;
- оператор не конструирует произвольные журналы;
- опубликованные редакции, зарегистрированные документы и исторические снимки не переписываются;
- управление и ведение моделируются раздельно;
- информационное ведение — характеристика ведения;
- ЩПТ и ШОТ относятся к общей технической группе оборудования системы оперативного постоянного тока; различие сохраняется как исходное обозначение или вариант исполнения;
- электронный, гибридный и бумажный режимы наряда не объявляются юридически эквивалентными без доказанного нормативного основания.

## 6. Качество изменения

Изменение считается технически готовым только после:

- проверки diff и отсутствия случайных файлов;
- Ruff, compileall и Django system checks;
- `makemigrations --check --dry-run`;
- миграций на PostgreSQL;
- профильных gate и тестов;
- полного актуального test suite;
- контейнерного smoke для затрагиваемого контура;
- обновления документации состояния;
- зелёного CI.

Техническая готовность не равна пользовательской приёмке.

## 7. Документационный контракт

Каждое принятое изменение обязано обновить релевантные документы:

- `docs/project/CURRENT_STATE.md`;
- `docs/project/CURRENT_HANDOFF.md`;
- `docs/project/OPEN_ITEMS.md`;
- `docs/project/DECISION_LOG.md`, если принято архитектурное или предметное решение;
- `docs/project/BASELINE_HISTORY.md` и `docs/project/ACCEPTANCE_HISTORY.md` после принятия;
- `docs/releases/RELEASE_NOTES.md` для значимого изменения;
- `docs/project/MODULE_MAP.md`, если изменился статус модуля.

Не дублировать одну и ту же истину в нескольких несовместимых вариантах.

## 8. Безопасность данных

Запрещено коммитить:

- пароли, private keys, tokens и содержимое `.env`;
- реальные персональные данные работников;
- фактические оперативные записи;
- внутренние рабочие инструкции, PDF/XLSX/CSV и архивы предприятия;
- базы данных, dumps, backups, логи с чувствительными данными;
- материалы, право на публикацию которых не подтверждено.

Допустимо хранить технические IP-адреса, пути, имена сервисов и команды в закрытом репозитории, если они не содержат секретов.

## 9. Правила ответа пользователю

- русский язык;
- точные и готовые команды;
- один этап выполнения за раз, когда требуется ручная проверка;
- не просить пользователя вручную собирать файлы или исправлять код;
- не объявлять успех без логов, CI или иной проверяемой опоры;
- явно разделять факт, вывод и план;
- критически оспаривать неверные или рискованные предположения.

## 10. Merge

Никогда не выполнять merge по собственной инициативе. Формулировки пользователя вроде «мёрджим», «сливай», «принимаю» или их однозначный эквивалент являются разрешением. До этого PR остаётся open, при необходимости draft.
