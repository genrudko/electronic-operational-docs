# Проект электронной оперативной документации
## Окончательный план разработки v1.0

**Кодовое название:** «План-капкан»  
**Статус:** утверждённая базовая линия разработки  
**Формат работы:** ассистент готовит автономные патчи; пользователь применяет их локально, проверяет логовый и визуальный результат и передаёт результаты для следующей итерации.

---

# 1. Цель проекта

Создать независимый универсальный прототип модульной системы электронной оперативной документации для электроэнергетики РФ, который:

- облегчает работу оперативного персонала;
- не привязан к конкретной ВЭС, SCADA, АСУ ТП, CIM-модели или однолинейной схеме;
- использует настраиваемые справочники предприятия, объектов, персонала и документов;
- проектируется с учётом требований к электронному ведению документации;
- может быть впоследствии официально испытан и введён предприятием в эксплуатацию;
- сохраняет возможность подключения новых модулей без переписывания нормативного ядра.

До официального решения работодателя система является независимым демонстрационным прототипом. В ней не используются реальные персональные данные, производственные учётные записи, действующие документы и подключения к корпоративной или технологической инфраструктуре.

# 3. Архитектурная базовая линия

## 3.1. Стиль архитектуры

**Модульный монолит.**

Причины:

- единая транзакция документа, подписи и аудита;
- проще обеспечить целостность и тестируемость;
- проще разворачивать и резервировать;
- меньше инфраструктурных компонентов;
- модули изолируются внутри приложения и при необходимости могут быть выделены позднее.

## 3.2. Технологический стек

- Python 3.13;
- Django 5.2 LTS;
- PostgreSQL 18;
- серверные Django-шаблоны;
- HTMX подключается позднее только для полезных интерактивных сценариев;
- обычный CSS с собственной компактной дизайн-системой;
- Docker Compose для локальной PostgreSQL;
- pytest или Django TestCase;
- Ruff для статической проверки;
- mypy вводится после стабилизации моделей;
- Linux как целевая серверная среда;
- Windows поддерживается как локальная среда разработки.

## 3.3. Слои

```text
Presentation
    Django views/templates/forms
Application
    use cases, workflows, permissions
Domain
    documents, versions, signatures, transitions
Infrastructure
    PostgreSQL, files, backup, time, authentication
```

Бизнес-правила не должны находиться только во views, шаблонах или JavaScript.

# 4. Основные инварианты

Эти правила не могут быть отменены ради удобства интерфейса.

1. Черновик можно редактировать.
2. Зарегистрированную версию нельзя редактировать.
3. Подписанную версию нельзя физически удалить.
4. Исправление создаёт новую связанную версию или корректирующий документ.
5. Аннулирование является отдельным подписываемым событием.
6. Серверное время является источником времени регистрации и подписи.
7. Факт входа в систему не равен электронной подписи.
8. Подпись относится к конкретному зафиксированному содержанию.
9. Старые подписи сохраняют сведения о должности и полномочиях на момент подписания.
10. Администратор инфраструктуры не может подписывать или изменять документы за работников.
11. Каждое юридически значимое действие создаёт неизменяемое событие аудита.
12. Физическое удаление допускается только для технического пустого черновика по формализованному правилу.
13. Оборудование является необязательной ссылкой, а не обязательным фундаментом документа.
14. Система должна работать без SCADA, CIM и внешних корпоративных сервисов.
15. Каждый нормативный инвариант должен иметь автоматический или приёмочный тест.

# 6. Жизненные циклы

## 6.1. Универсальная версия документа

```text
DRAFT
  ├── REGISTERED
  │      ├── CORRECTION_CREATED
  │      └── ANNULLED
  └── DISCARDED
```

## 6.2. Оперативная запись

```text
DRAFT
→ REGISTERED
→ ACKNOWLEDGED (опционально)
→ EXECUTED (для поручения)
→ CLOSED (для контролируемой записи)
```

## 6.3. Заявка

```text
DRAFT
→ SUBMITTED
→ UNDER_REVIEW
→ AGREED
→ AUTHORIZED
→ IN_PROGRESS
→ COMPLETED
→ CLOSED
```

Допустимы возврат на доработку, отклонение, отмена, приостановка и согласование с изменениями.

## 6.4. Дефект

```text
DRAFT
→ REGISTERED
→ CONFIRMED
→ ASSIGNED
→ IN_PROGRESS
→ ELIMINATED
→ VERIFIED
→ CLOSED
```

Допустимы отклонение, перенос срока, повторное открытие и аннулирование ошибочной регистрации.

## 6.5. Журнал нарядов и распоряжений

```text
DRAFT
→ REGISTERED
→ WORKPLACE_PREPARATION
→ ADMITTED
→ IN_PROGRESS
→ INTERRUPTED
→ IN_PROGRESS
→ COMPLETED
→ CLOSED
```

# 8. Правила патчей

Каждый патч имеет:

- уникальный номер;
- одну основную цель;
- описание затрагиваемых инвариантов;
- предварительную проверку состояния;
- резервное копирование изменяемых файлов либо безопасный отказ;
- подробный лог;
- автоматический gate;
- команды запуска;
- перечень ожидаемых визуальных изменений;
- процедуру отката;
- финальный маркер успешного завершения.

Именование:

```text
patch_001_bootstrap.py
patch_002_organizational_core.py
patch_003_document_kernel.py
...
```

Логи:

```text
logs/patch_001_bootstrap.log
logs/patch_002_organizational_core.log
...
```

Патч не считается завершённым только потому, что код записан. Он завершён, когда:

1. применился без ошибки;
2. gate прошёл;
3. пользователь проверил интерфейс;
4. лог проанализирован;
5. замечания закрыты либо внесены в следующий патч.

# 12. Критерий успеха первой очереди

Первая очередь успешна, если независимый пользователь может:

1. принять тестовую смену;
2. создать и подписать оперативную запись;
3. исправить её без изменения исходной версии;
4. зарегистрировать дефект;
5. создать на его основании заявку;
6. зарегистрировать связанный наряд или распоряжение;
7. отразить допуск в оперативном журнале;
8. закрыть цепочку документов;
9. найти всю историю;
10. проверить подписи и целостность;
11. распечатать документы;
12. восстановить систему из backup.
