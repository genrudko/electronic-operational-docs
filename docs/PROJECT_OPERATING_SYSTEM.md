# Операционная система проекта ЭОД

**Статус:** обязательный рабочий регламент разработки независимого демонстрационного прототипа ЭОД.

Этот документ определяет не функциональные требования к системе, а порядок, по которому изменения проектируются, реализуются, проверяются, принимаются и включаются в стабильную ветку.

## 1. Цель модели

Разработка организована так, чтобы человек не выполнял механические операции программирования и администрирования проекта.

Распределение ответственности:

| Область | Ответственный |
|---|---|
| Цели продукта, предметные правила энергетики, приоритеты | владелец продукта и доменный эксперт |
| Архитектура, реализация, тесты, документация, анализ дефектов | AI-разработчик |
| Хранение истории, pull request, CI и контроль веток | GitHub |
| Исполнение Django, PostgreSQL, миграций и проверок | изолированный development-контур VPS |
| Функциональная и визуальная приёмка | владелец продукта |
| Разрешение на merge и изменение стабильного baseline | только владелец продукта |

Человек остаётся в точках, где требуется предметное решение или оценка результата, но исключается из ручного редактирования кода, сборки файлов, применения patch-скриптов и исправления технических ошибок.

## 2. Основные инварианты

1. `main` содержит только принятые изменения.
2. Обычная разработка никогда не выполняется непосредственно в `main`.
3. Каждый work item выполняется в отдельной ветке и проходит через pull request.
4. VPS использует read-only deploy key и не создаёт commits, pull requests или merges.
5. Нормальный цикл не включает скачивание, загрузку или ручной запуск patch-файлов.
6. Стабильный preview и активный development имеют разные checkout, Compose projects, базы, пользователей, volumes, сети и порты.
7. Development-контур не запускается из `main`.
8. Preview не используется для разработки и не изменяется до принятого merge.
9. PostgreSQL является целевой СУБД для инфраструктурных и интеграционных gate-проверок.
10. Реальные персональные, оперативные и служебные данные не коммитятся в Git.
11. Merge выполняется только после явного разрешения владельца продукта.
12. Зелёный CI не заменяет предметную и визуальную приёмку.

## 3. Источники истины

При противоречии используется следующий приоритет:

1. принятое решение владельца продукта в основном интеграционном контуре;
2. текущий принятый baseline ветки `main`;
3. утверждённые ADR и этот регламент;
4. действующий master plan проекта;
5. документация конкретного модуля и acceptance criteria;
6. код и автоматические тесты;
7. старые планы, архивные чаты и исторические patch-описания.

Старый документ не становится актуальным только потому, что он находится в репозитории. При расхождении с более новым принятым решением он должен быть обновлён или явно помечен как исторический.

## 4. Контуры исполнения

| Контур | Checkout | Ветка | Compose project | Приложение | База |
|---|---|---|---|---:|---|
| Accepted preview | `/srv/eod/repository` | только `main` | `eod-preview` | `127.0.0.1:8765` | `eod_preview` |
| Active development | `/srv/eod/development` | любая активная ветка, кроме `main` | `eod-development` | `127.0.0.1:8766` | `eod_development` |

Дополнительные правила:

- PostgreSQL ports не публикуются на host;
- доступ к приложениям выполняется через SSH tunnel;
- development может быть восстановлен копией принятой preview-базы;
- сброс development не должен записывать данные в preview;
- локальный ПК или смартфон являются только клиентами: SSH, браузер, запись видео и передача результата приёмки.

## 5. Единица работы

Каждое изменение оформляется как самостоятельный work item одного из типов:

- `feature` — новая пользовательская или доменная возможность;
- `fix` — исправление дефекта;
- `repair` — корректирующее изменение после неуспешной проверки;
- `infra` — окружение, CI, deployment, backup или эксплуатационная безопасность;
- `docs` — регламент, ADR, runbook или проектная документация;
- `research` — доказательное исследование, которое ещё не меняет runtime-код.

Рекомендуемое имя ветки:

```text
<type>/<номер>-<краткое-название>
```

Примеры:

```text
feature/012-structured-journals
fix/012-equipment-picker-focus
infra/003-isolated-vps-development
docs/001-project-operating-system
```

Ветка создаётся от текущего принятого `main`, а не от устаревшего локального состояния.

## 6. Жизненный цикл изменения

### 6.1. Постановка

Владелец продукта задаёт цель, предметные ограничения, ожидаемое поведение и приоритет.

AI-разработчик обязан:

- восстановить текущий baseline;
- проверить связанные решения и документацию;
- выявить риски и противоречия;
- не подменять предметное решение техническим предположением;
- сформировать acceptance criteria до или одновременно с реализацией.

### 6.2. Реализация

AI-разработчик изменяет активную ветку непосредственно через GitHub.

Нормальный поток:

```text
AI → commit в feature branch → GitHub CI → VPS git pull --ff-only
```

VPS не используется как автор изменений. Ручное редактирование файлов на VPS запрещено, кроме аварийной диагностики, которая не должна оставлять незафиксированный код.

### 6.3. Автоматические gate-проверки

Минимальный набор выбирается по риску изменения.

| Gate | Когда обязателен |
|---|---|
| синтаксис, format и lint | любое изменение кода или scripts |
| Django `check` | любое изменение приложения или settings |
| `makemigrations --check --dry-run` | модели, migrations, импортеры, документарное ядро |
| unit и integration tests | любая затронутая доменная логика |
| PostgreSQL tests | транзакции, блокировки, нумерация, migrations, imports |
| container smoke | Docker, startup, settings, dependencies, deployment |
| development isolation smoke | изменение development-контура |
| security/privacy gate | auth, права, secrets, data import, repository policy |

Ноль обнаруженных тестов или запуск ниже установленного порога считается ошибкой, а не успешной проверкой.

### 6.4. Развёртывание в development

После зелёного CI активный checkout VPS синхронизируется только fast-forward операциями:

```bash
cd /srv/eod/development
git fetch --prune origin
git pull --ff-only
```

Далее:

- `refresh` — Python, templates, CSS, JavaScript и обычные source changes;
- `rebuild` — dependencies, Dockerfile или container startup;
- `migrate` — явное применение migrations, когда это требуется;
- `reset_development_database.sh` — безопасное восстановление development из accepted preview.

### 6.5. Техническая проверка на VPS

До передачи на приёмку должны быть подтверждены:

- правильная активная ветка и HEAD;
- чистый worktree;
- healthy application и database containers;
- правильная database identity;
- успешный health endpoint;
- HTTP 200 основной страницы;
- обязательные checks и tests;
- отсутствие воздействия на preview.

### 6.6. Приёмка владельцем продукта

Владелец продукта проверяет результат через browser tunnel и оценивает:

- соответствие предметной логике;
- полноту сценария;
- понятность интерфейса;
- отсутствие регрессий;
- пригодность для внутреннего показа;
- визуальное качество;
- фактическое выполнение acceptance criteria.

Результат приёмки:

- `accepted` — разрешена подготовка к merge;
- `accepted with follow-up` — текущий scope принят, замечания вынесены отдельно;
- `repair required` — ветка остаётся открытой, выполняется корректирующее изменение;
- `rejected` — решение не соответствует цели и требует пересмотра.

### 6.7. Merge

Перед merge обязательно:

- PR не draft;
- актуальный head прошёл обязательный CI;
- review threads разрешены или явно приняты;
- VPS development проверен;
- владелец продукта дал явное разрешение;
- expected head SHA зафиксирован при merge, чтобы исключить подмену ветки между приёмкой и слиянием.

Предпочтительный метод — обычный merge commit, сохраняющий границу work item и историю его review.

### 6.8. Обновление accepted preview

После merge:

1. фиксируется новый `main` SHA;
2. `/srv/eod/repository` обновляется `git pull --ff-only origin main`;
3. preview пересобирается или перезапускается только когда это необходимо изменениями;
4. выполняется post-merge health gate;
5. при migrations или data changes выполняются backup и контролируемое применение;
6. новый SHA становится принятым baseline только после успешной проверки.

Отсутствие отдельного post-merge CI или VPS gate нельзя описывать как успешно пройденную проверку.

## 7. Definition of Done

Work item завершён только когда выполнены все применимые пункты:

- [ ] scope и acceptance criteria определены;
- [ ] изменения находятся в отдельной ветке;
- [ ] код, migrations, tests и документация согласованы;
- [ ] обязательные CI gates зелёные;
- [ ] development развёрнут на точном принятом head;
- [ ] технические проверки VPS пройдены;
- [ ] предметная и визуальная приёмка выполнена;
- [ ] владелец продукта явно разрешил merge;
- [ ] PR merged;
- [ ] accepted preview синхронизирован и healthy;
- [ ] новый baseline SHA зафиксирован;
- [ ] follow-up defects оформлены отдельно и не потеряны.

## 8. Изменения базы данных

Для migrations, imports и преобразования данных обязательны:

1. проверка направления миграции и совместимости с текущими данными;
2. backup до разрушительной операции;
3. прогон на отдельной development-базе;
4. проверка counts, ключевых объектов и demo authentication;
5. запрет записи в preview до принятого merge;
6. явный план rollback или восстановления из backup;
7. фиксация пути к backup и результата restore gate.

Демонстрационные данные должны быть безопасными. Реальные персональные данные, внутренние номера, пароли, оперативные схемы и производственные документы не допускаются в Git и CI artifacts.

## 9. Repair-процесс

Неуспешный CI, лог, видео или приёмка не исправляются вручную пользователем.

Процесс:

```text
результат проверки → анализ причины → repair commit → повторный CI → повторное VPS-развёртывание → повторная приёмка
```

Repair остаётся в той же ветке и PR, если не меняет исходную цель work item. Новый scope оформляется отдельной веткой.

## 10. Аварийный режим

Patch-файл, ручное копирование или локальное применение допускаются только когда прямой commit в GitHub технически невозможен.

Аварийное изменение должно:

- выполняться только в `/srv/eod/development`;
- никогда не применяться в `/srv/eod/repository`;
- быть немедленно воспроизведено нормальным commit в GitHub;
- не приниматься и не merge-иться, пока GitHub branch не станет источником точного проверенного состояния;
- не требовать writable deploy key на VPS.

## 11. Запрещённые действия

- прямой commit или push в `main`;
- force-push в `main`;
- разработка в accepted preview checkout;
- запуск development stack из `main`;
- общий `.env` для preview и development;
- общий PostgreSQL volume для двух контуров;
- публикация PostgreSQL port;
- хранение secrets, backups, logs, databases и реальных документов в Git;
- ручное исправление пользователем сгенерированного кода;
- merge без явного разрешения владельца продукта;
- заявление об успешной проверке без фактического доказательства.

## 12. Минимальный журнал доказательств PR

Для каждого значимого PR фиксируются:

- base SHA;
- head SHA;
- список затронутых областей;
- migrations и data impact;
- CI run IDs и conclusions;
- development branch и database identity;
- health и HTTP gate;
- результат функциональной/визуальной приёмки;
- известные ограничения;
- явное разрешение на merge;
- merge commit SHA;
- post-merge baseline и результат preview gate.

Это превращает историю GitHub в воспроизводимый журнал разработки и приёмки, а не только в набор изменений файлов.
