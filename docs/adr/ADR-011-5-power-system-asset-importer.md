# ADR-011.5 — предметный импорт объектов энергосистемы

**Статус:** принято
**Дата:** 22.07.2026
**Патч:** 011.5 — Power System Asset Importer

## Контекст

Исходный перечень объектов диспетчеризации содержит энергообъекты, иерархические
узлы, первичное и вспомогательное оборудование, РЗА, СДТУ, управление, ведение,
алиасы и проблемы качества источника. Его нельзя напрямую загружать в рабочий
реестр: одинаковые локальные наименования повторяются в разных КТП и ВЭУ,
некоторые строки описывают один логический объект, часть родительских путей
требует восстановления, а конфликтные строки должны оставаться доступными для
проверки без блокирования всего пакета.

Реальные перечни оборудования не входят в Git и не встраиваются в патч. Патч
создаёт только механизм контролируемой загрузки нормализованного ZIP-пакета.

## Решение

### 1. Контролируемый конвейер

Публикация выполняется только по цепочке:

`source revision → staging → dry-run/review → publication`.

Загрузка ZIP-пакета не изменяет рабочие справочники. Публикация требует прямой
роли администратора справочников, повторной аутентификации и проверки SHA-256
канонического снимка.

### 2. Исходная строка и логический объект разделены

`PowerSystemAssetOccurrence` хранит неизменяемое происхождение строки. Один
логический объект может иметь несколько source occurrences. Решения
`ACCEPT_AS_NEW`, `MERGE_WITH`, `EXCLUDE` не переписывают исходные значения.

### 3. Построчный карантин

Каждая строка получает одно из состояний:

- `READY`;
- `REVIEW_REQUIRED`;
- `BLOCKED`;
- `EXCLUDED`;
- `PUBLISHED`.

Конфликт отдельной строки не блокирует публикацию остальных готовых строк.

### 4. Имена и алиасы

Хранятся отдельно:

- исходное диспетчерское наименование;
- нормализованное отображение;
- ключ сравнения;
- scoped alias.

Алиас может быть глобальным, ограниченным энергообъектом либо родительским
объектом. Глобальная уникальность локальных диспетчерских вариантов запрещена.

### 5. Иерархия

Родительство восстанавливается из контекста источника, а не принимается из
`hierarchy_path_raw` без проверки. Публикация выполняется в порядке зависимостей;
объект без опубликованного или одновременно публикуемого родителя не создаётся.

### 6. Управление и ведение

Оперативное управление и оперативное ведение публикуются раздельно.
Для ведения используется контролируемый режим:

- `OPERATIONAL`;
- `INFORMATIONAL`;
- `UNKNOWN`.

Пустое значение, явное отсутствие назначения и назначенный субъект различаются.
Неоднозначный субъект остаётся в review и не создаётся автоматически.

### 7. Идемпотентность и редакции

Повторная загрузка того же ZIP с тем же SHA-256 открывает существующую редакцию
и не создаёт дублей. Новая версия того же источника сравнивается по
`occurrence_id` и содержательным SHA-256 строк.

### 8. Данные и безопасность

Патч не содержит реальных объектов, диспетчерских наименований или матриц
управления/ведения. Такие данные загружаются локально в подходящий профиль и не
коммитятся в Git.

## Последствия

- Общий импорт Patch 011.4 остаётся фундаментом профилей и безопасной публикации.
- Предметный импорт оборудования использует собственный строгий пакетный
  контракт, поскольку иерархия и полномочия не выражаются обычной плоской
  таблицей без потери смысла.
- Неоднозначные связи РЗА, линейные концы и merge-кандидаты сохраняются как
  предложения и не объявляются подтверждённой топологией.
- Рабочая SQLite-база мигрируется самим автономным патчем после резервного
  копирования; отдельно проверяется чистая изолированная база.

## Профиль проверки

Patch 011.5 относится к высокому риску из-за новых моделей, миграций и
публикации в несколько реестров. Обязательны Ruff, compileall, Django checks,
проверка миграций на чистой и рабочей БД, профильный gate, тесты equipment,
dispatching и imports, а также полный test discovery.
