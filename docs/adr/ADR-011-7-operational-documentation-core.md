# ADR-011.7 — единое ядро структурированной оперативной документации

**Статус:** принято для демонстрационного прототипа
**Дата:** 23.07.2026
**Patch:** 011.7

## Контекст

После импорта оборудования, персонала, прав и перечня документации необходимо перейти от отдельных справочников к рабочим структурированным журналам. Заявки, распоряжения, дефекты, работы, ключи и другие журналы имеют разные предметные поля, но используют одинаковые системные механизмы: нумерацию, состояния, участников, оборудование, документы-основания, связи, поиск и историю.

Создание отдельного независимого Django-приложения для каждого журнала привело бы к дублированию кода, расхождению гарантий и усложнению последующего изменения локальных форм.

## Решение

Создаётся приложение `apps.operational_documents`, содержащее общее ядро структурированной оперативной документации.

### 1. Стабильный тип и публикуемая редакция

`OperationalDocumentType` является стабильной идентичностью вида журнала или документа в пределах организации.

`OperationalDocumentTypeRevision` содержит конкретную конфигурацию:

- предметные поля и их типы;
- признаки обязательности, поиска и показа в общем реестре;
- состояния;
- разрешённые переходы;
- обязательность комментария при переходе;
- роли участников;
- правила нумерации;
- обязательность рабочего места.

Опубликованная редакция получает канонический JSON-снимок и SHA-256 и после публикации не изменяется. Новые правила должны оформляться новой редакцией. Запись навсегда сохраняет ссылку на редакцию, по которой создана.

### 2. Общая запись

`OperationalDocumentRecord` хранит:

- организацию и тип;
- опубликованную редакцию структуры;
- серверный регистрационный номер;
- время события;
- заголовок и краткое содержание;
- рабочее место и его текстовый снимок;
- текущее состояние и его снимок;
- нормализованные значения предметных полей;
- автора и снимки Ф.И.О., должности и подразделения;
- номер текущей версии;
- поисковый текст.

Идентификационные реквизиты записи, номер и исходная редакция структуры неизменяемы.

### 3. Серверная нумерация

Номер формируется внутри транзакции по паре `тип + год`. Формат задаётся опубликованной редакцией: `<PREFIX>-<YEAR>-<SEQUENCE>`. Номер не вводится пользователем и не переиспользуется.

### 4. Связи и снимки справочников

Запись может содержать:

- участников с конфигурируемыми ролями;
- оборудование;
- зарегистрированные документы-основания;
- связи с другими структурированными записями.

Для отображения исторического состояния сохраняются текстовые снимки участника, должности, подразделения, рабочего места, оборудования, диспетчерского наименования и связанного документа. Связи между разными организациями запрещены.

### 5. История и аудит

Каждое создание, изменение и переход состояния:

1. увеличивает версию записи;
2. создаёт неизменяемый канонический снимок `OperationalDocumentRecordRevision`;
3. вычисляет SHA-256;
4. создаёт append-only событие `OperationalDocumentAuditEvent`.

Физическое удаление записей, редакций, типов и событий аудита запрещено. Массовое изменение защищённых моделей через QuerySet также запрещено.

### 6. Общий интерфейс

Patch 011.7 предоставляет:

- реестр всех структурированных оперативных записей организации;
- полнотекстовый поиск по номеру, заголовку, содержанию, предметным полям, участникам, оборудованию и документам;
- фильтры по типу, состоянию, рабочему месту, оборудованию и датам;
- мастер создания первого типа с публикацией неизменяемой редакции;
- динамическую форму записи по опубликованной схеме;
- карточку записи со связями, доступными переходами, редакциями и техническим аудитом.

## Границы Patch 011.7

В Patch 011.7 не фиксируются окончательные предметные модели заявок, распоряжений, дефектов и иных журналов. Он предоставляет механизм и демонстрационный конструктор. Конкретный набор журналов и их начальные конфигурации создаются Patch 011.8.

Оперативный журнал остаётся отдельным специализированным модулем, поскольку требует последовательного свободного текста, редактора, шаблонов и механики передачи смены.

## Безопасность прототипа

- ядро работает в пределах организации активного сотрудника;
- публикация типов разрешена только суперпользователю или роли `shift_supervisor`;
- все предметные связи проверяются по организации;
- запись не является юридически значимым электронным оригиналом без отдельного решения о подписях и режиме документооборота;
- Patch 011.7 не отменяет бумажные формы и не заявляет промышленную готовность.

## Последствия

Положительные:

- журналы 011.8 создаются конфигурацией поверх одного механизма;
- единые гарантии нумерации, истории и аудита;
- локальные формы можно версионировать без переписывания ядра;
- общие поиск, фильтры и связи доступны всем типам.

Ограничения:

- редактор произвольных статусов и переходов в пользовательском интерфейсе пока не реализован; первая редакция получает безопасный стандартный цикл;
- сложные доменные запреты конкретных журналов добавляются специализированными правилами следующих патчей;
- PostgreSQL-конкурентность окончательно проверяется на этапе Linux/PostgreSQL Readiness.
