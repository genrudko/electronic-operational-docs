# ADR-011.7 — единое ядро структурированной оперативной документации

**Статус:** принято для демонстрационного прототипа
**Дата:** 24.07.2026
**Patch:** 011.7 Repair 2

## Контекст

Заявки, распоряжения, дефекты, работы, ключи и другие журналы используют общие системные механизмы: нумерацию, участников, оборудование, документы-основания, связи, поиск, историю и аудит. При этом состав граф, назначение и правила ведения каждого журнала уже установлены утверждёнными инструкциями и не должны конструироваться оперативным персоналом.

Создание отдельного независимого Django-приложения для каждого журнала привело бы к дублированию кода. Сведение всех журналов к произвольной пользовательской анкете, напротив, разрушило бы утверждённые формы и предметные правила.

## Решение

Создаётся приложение `apps.operational_documents`, содержащее общее техническое ядро структурированной оперативной документации.

### 1. Стабильный тип и публикуемая редакция

`OperationalDocumentType` является стабильной идентичностью формы журнала в пределах организации.

`OperationalDocumentTypeRevision` содержит конкретную конфигурацию:

- предметные поля и их типы;
- признаки обязательности, поиска и показа в общем реестре;
- состояния и разрешённые переходы;
- роли участников;
- правила нумерации;
- обязательность рабочего места.

Опубликованная редакция получает канонический JSON-снимок и SHA-256 и после публикации не изменяется. Новые правила оформляются новой редакцией. Запись сохраняет ссылку на редакцию, по которой создана.

### 2. Общая запись

`OperationalDocumentRecord` хранит организацию, форму журнала, опубликованную редакцию, серверный номер, время события, рабочее место, значения полей, участников, оборудование, документы, связи, текущее состояние и поисковый индекс.

Идентификационные реквизиты, номер и исходная редакция структуры неизменяемы.

### 3. Серверная нумерация

Номер формируется внутри транзакции по паре `тип + год`. Номер не вводится пользователем и не переиспользуется.

### 4. Связи и снимки справочников

Запись может содержать участников, оборудование, зарегистрированные документы-основания и связи с другими структурированными записями. Для исторического отображения сохраняются текстовые снимки справочных данных. Межорганизационные связи запрещены.

### 5. История и аудит

Каждое создание, изменение и переход состояния создаёт новую неизменяемую редакцию записи и append-only событие аудита. Физическое удаление и массовое изменение защищённых сущностей запрещены.

### 6. Источник формы обязателен

Пользовательский интерфейс не предоставляет конструктор произвольного журнала. Рабочая форма устанавливается только автономным source-bound патчем, в котором явно зафиксированы:

- наименование утверждённого документа;
- раздел инструкции;
- приложение с формой;
- точный состав и порядок граф;
- специальные правила и действия;
- тесты соответствия источнику.

Оперативный персонал создаёт записи только по установленным формам. Технические схемы, созданные для проверки ядра, сохраняются для аудита и просмотра, но не допускают новых записей, изменений и переходов.

### 7. Пользовательский интерфейс

Пользовательский слой показывает каталог утверждённых форм, общий реестр, карточки записей и предметные действия. Системные коды, SHA-256 и внутренний аудит вынесены в технические сведения. Выбор оборудования, документов и участников поддерживает поиск и обычный щелчок без удерживания Ctrl.

## Границы Patch 011.7

Patch 011.7 реализует механизмы общего ядра и source-bound границу. Он не устанавливает окончательные графы журналов заявок, распоряжений, дефектов и иных журналов. Эти формы создаются в Patch 011.8 строго по утверждённым приложениям.

Оперативный журнал остаётся отдельным специализированным модулем.

## Безопасность прототипа

- ядро работает в пределах организации активного сотрудника;
- ручное создание форм в пользовательском интерфейсе отключено;
- техническая конфигурация доступна только для диагностики;
- бумажные формы не отменяются;
- система не заявляется юридически значимым электронным оригиналом без отдельного решения владельца объекта.

## Последствия

Положительные:

- общие гарантии нумерации, истории, аудита и связей сохраняются;
- утверждённые журналы не превращаются в бесформенную таблицу;
- изменение инструкции оформляется новой source-bound редакцией;
- оператор работает с готовой формой, а не с техническим конструктором.

Ограничения:

- до Patch 011.8 новые рабочие записи недоступны, если утверждённая форма ещё не установлена;
- доменные правила конкретных журналов реализуются вместе с их формами;
- PostgreSQL-конкурентность проверяется на позднем readiness-этапе.
