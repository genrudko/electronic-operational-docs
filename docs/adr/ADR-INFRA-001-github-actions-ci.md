# ADR-INFRA-001 — GitHub Actions CI с PostgreSQL

**Статус:** принято для интеграционного контура
**Дата:** 24.07.2026
**Ветка реализации:** `infra/001-ci-baseline`

## Контекст

До этого этапа основная техническая приёмка выполнялась автономными локальными patch-runner скриптами на Windows. Такой процесс сохранял rollback и подробные проверки, но не доказывал воспроизводимость проекта на чистом Linux и PostgreSQL и требовал ручного запуска на рабочем компьютере.

В репозитории накоплены `scripts/gate_patch_*.py`. Они создавались как контракты конкретных исторических патчей и не образуют кумулятивный набор: поздние рефакторинги могут намеренно менять пути, тексты и структуры, которые требовали ранние gates.

## Решение

Создаётся постоянный workflow `.github/workflows/ci.yml`.

CI использует:

- GitHub-hosted runner Ubuntu 24.04;
- Python 3.13;
- PostgreSQL 18.4 как service container;
- установку проекта и dev-зависимостей из `pyproject.toml`;
- Ruff;
- `compileall`;
- Django system check;
- `makemigrations --check --dry-run`;
- применение всех миграций на PostgreSQL;
- актуальный архитектурный gate принятого baseline;
- `collectstatic`;
- полный последовательный Django test suite;
- проверку отсутствия незаявленных изменений рабочего дерева.

`GITHUB_TOKEN` получает только `contents: read`.

## Политика архитектурных gates

Постоянный CI не запускает все исторические `gate_patch_*.py` подряд.

Для текущего baseline запускается `scripts/gate_patch_011_7.py`, обновлённый в принятом Patch 011.7 Repair 2. При следующем архитектурном патче список текущих gates должен быть пересмотрен явно вместе с workflow.

Исторические gates сохраняются в репозитории как доказательства и диагностические контракты соответствующих патчей, но не считаются автоматически совместимыми с текущей структурой проекта.

Полный Django test suite остаётся основной кумулятивной регрессионной проверкой поведения.

## Границы

В INFRA-001 не входят:

- deployment на VPS;
- Dockerfile приложения и серверный Compose;
- домен и HTTPS;
- reverse proxy;
- production-секреты;
- self-hosted GitHub Actions runner;
- автоматическое слияние в `main`.

## Проверенный результат

На commit `a4f2166102c86884f77dabc1553823dc88576df1` GitHub Actions успешно выполнил весь workflow на Ubuntu 24.04, Python 3.13 и PostgreSQL 18.4, включая текущий архитектурный gate, полный Django test suite и контроль чистоты checkout.

## Последствия

Положительные:

- Linux/PostgreSQL совместимость проверяется на каждом изменении;
- ошибки миграций и зависимостей обнаруживаются до развёртывания;
- VPS не используется как CI runner или рабочее место разработчика;
- переход к контейнерному preview опирается на воспроизводимый зелёный baseline.

Ограничения:

- workflow пока не собирает образ приложения;
- preview-развёртывание выполняется отдельным этапом INFRA-002;
- branch protection и обязательные status checks настраиваются после принятия первого CI baseline.
