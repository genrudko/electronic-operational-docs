# ADR-007.4: организационная структура, обслуживание объектов и профиль запуска

## Статус

Принято для независимого демонстрационного прототипа.

## Контекст

Визуальная приёмка Patch 007.3 показала две независимые проблемы:

1. интерфейс мог запускаться на старой SQLite-базе из унаследованной переменной `SQLITE_PATH`, хотя чистая `presentation.sqlite3` была создана;
2. упрощённая структура из одного подразделения не отражала реальную организацию работы нескольких энергообъектов общим персоналом.

Организационная иерархия, обслуживание энергообъектов, допуски персонала и оперативная подчинённость являются разными отношениями и не должны выводиться друг из друга автоматически.

## Решение

### Организационная иерархия

В презентационном профиле используется официальный вариант сокращения **ЦОТУиЭ ВЭС Невинномысск**. Внутри центра отражаются профильные группы, отдел и участки. Руководители центра относятся непосредственно к ЦОТУиЭ и не выделяются в вымышленное структурное подразделение «Руководство».

Участок ТОиР лопастей ВЭУ моделируется отдельным подразделением блока главного инженера. Он не входит в ЦОТУиЭ, но территориально базируется в Невинномысске и обслуживает ВЭС нескольких территорий.

### Энергообъекты

Кочубеевская ВЭС, Кузьминская ВЭС и ПС 330 кВ Барсуки хранятся как энергообъекты, а не организационные подразделения.

Связь `DivisionEnergySiteService` явно показывает, какое подразделение и в каком качестве обслуживает конкретный энергообъект.

### Персонал

Сотрудник хранится одной записью. `EmployeeEnergySiteAuthorization` задаёт перечень объектов и роль, в которой сотрудник может быть назначен. В презентационном профиле начальники смен и дежурные электромонтёры имеют допуск ко всем трём объектам.

Фактический состав конкретной смены в эту модель не включается; он относится к будущему модулю сменных назначений.

### Оперативная подчинённость

`OperationalReportingLine` отделяет оперативную подчинённость от административного дерева и от диспетчерского/технологического управления оборудованием.

Для участка оперативного обслуживания непосредственным оперативным руководителем задан заместитель технического директора по оперативной работе.

### Безопасность демонстрационных данных

Сохраняются вымышленные полные ФИО. Реальные ФИО, электронные адреса, телефоны, псевдонимы и табельные номера со скриншотов не переносятся.

### Профиль SQLite

Обычный запуск использует `data/presentation.sqlite3`. Унаследованный `SQLITE_PATH` игнорируется, пока явно не включён `EOD_ALLOW_SQLITE_PATH_OVERRIDE=1`.

`run_dev.ps1` принудительно выбирает презентационный профиль и удаляет `SQLITE_PATH` из окружения текущего процесса. Gate и patch-скрипты используют явный изолированный профиль с разрешённым override.

## Последствия

- организационная принадлежность больше не подменяет зону обслуживания;
- отдельный участок лопастей корректно отображается рядом с ЦОТУиЭ;
- общий оперативный персонал не дублируется по энергообъектам;
- интерфейс показывает чистую презентационную базу независимо от старого значения `SQLITE_PATH`;
- автоматический push не выполняется; результат фиксируется локальным commit.

## Repair 1 — совместимость health API и отображение полного наименования

Первый полный прогон Patch 007.4 выявил два регрессионных дефекта, не связанных
с моделью организационной структуры:

1. расширенный health-ответ содержал `database_profile`, но перестал возвращать
   исторический совместимый ключ `profile`;
2. карточка организации использовала только `short_name`, поэтому организация
   без заполненного краткого наименования отображалась с пустым заголовком.

Repair 1 сохраняет новый явный профиль базы данных, возвращает совместимое поле
health API и использует полное наименование организации как безопасный fallback.
Модель ЦОТУиЭ, отдельного участка ТОиР лопастей, связей обслуживания,
объектовых допусков и оперативной подчинённости не изменяется.

## Repair 2 — совместимость диагностического вывода launcher

После успешного прохождения 197 тестов Repair 1 старый gate Patch 003.1
остановился на совместимости текстового вывода `run_dev.ps1`. Новый launcher
явно показывал презентационный профиль и файл `presentation.sqlite3`, но больше
не печатал историческую строку `Локальный профиль: SQLite`.

Repair 2 возвращает эту диагностическую строку и сохраняет новые, более точные
сведения о презентационном профиле и активном SQLite-файле. Выбор базы данных,
организационная структура, связи обслуживания, допуски персонала и оперативная
подчинённость не изменяются.

## Repair 3 — согласование заголовка организационной иерархии

После успешного прохождения 197 тестов и gate Patch 003–007.3 Repair 2
остановился на регистрозависимой проверке шаблона организационного справочника.
Шаблон содержал текст `ОРГАНИЗАЦИОННАЯ ИЕРАРХИЯ`, а gate искал точную строку
`Организационная иерархия`.

Repair 3 делает пользовательский заголовок основным и более понятным:
`Организационная иерархия`. Надзаголовок теперь обозначает содержимое блока:
`СТРУКТУРНЫЕ ПОДРАЗДЕЛЕНИЯ`. Организационная модель, данные, связи обслуживания,
допуски персонала, оперативная подчинённость и профиль базы не изменяются.

## Repair 4 — стилевой контракт новых организационных моделей

После успешного прохождения 197 тестов, всех gate Patch 003–007.4 и локальной
проверки безопасности Repair 3 остановился на четырёх замечаниях Ruff:

1. два организационных класса в импорте Django Admin располагались не по
   алфавиту;
2. в трёх новых моделях метод `clean()` находился перед методом `save()`,
   что не соответствует включённому Django style-контракту DJ012.

Repair 4 меняет только порядок импортов и методов. Содержимое методов,
ограничения моделей, миграции, презентационные данные, организационная структура,
связи обслуживания, допуски персонала и оперативная подчинённость не изменяются.
