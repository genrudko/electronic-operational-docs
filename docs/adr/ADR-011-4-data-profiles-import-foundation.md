# ADR-011.4 — Профили данных, основание импорта и технический английский

## Статус

Принято для Patch 011.4.

## Контекст

До наполнения реестров реальными диспетчерскими наименованиями, локальными ФИО и
перечнем документации необходимо явно разделить три контура данных:

1. безопасная презентационная база;
2. локальная проверочная база;
3. полностью синтетические автоматизированные тесты.

Существующий модуль `imports` уже обеспечивает staging, сопоставление колонок,
ручную проверку и транзакционную публикацию. Создание параллельного импортного
движка не требуется. Необходимо расширить существующий контур происхождением
данных и повторно используемыми схемами сопоставления.

Внутренние английские названия должны использовать профессиональную терминологию
электроэнергетики. Русские пользовательские, диспетчерские и нормативные
наименования сохраняются в исходном виде.

## Решение

### Профили данных

Вводится модель `DataProfile` с обязательными характеристиками:

- организация;
- стабильный код;
- тип профиля;
- уровень чувствительности;
- политика экспорта;
- допустимость реальных персональных данных;
- признак профиля по умолчанию;
- явное описание ограничений.

Для каждой организации автоматически создаются:

| Код | Назначение | Экспорт | Реальные ПДн |
|---|---|---|---|
| `presentation-safe` | безопасная предметная демонстрация | разрешён | запрещены |
| `local-validation` | локальная углублённая проверка | запрещён | допускаются |
| `automated-tests` | изолированные автоматизированные тесты | запрещён | запрещены |

Каждая `ImportBatch` обязательно связана с одним профилем. Профиль включается в
события импорта и в канонический снимок публикации версии
`eod.import.publication.v2`.

### Происхождение загрузки

В `ImportBatch` добавляются:

- `source_reference` — человекочитаемое наименование или реквизиты источника;
- `header_signature` — SHA-256 нормализованной структуры заголовков;
- `applied_mapping_template` — применённая сохранённая схема сопоставления.

Содержимое исходного файла после разбора по-прежнему не хранится.

### Схемы сопоставления

Вводится `ImportMappingTemplate`:

- область организации;
- назначение импорта;
- SHA-256 структуры заголовков;
- сопоставление `позиция колонки → поле реестра`;
- авторы создания и изменения;
- счётчик и время повторного применения.

После явного подтверждения сопоставления схема сохраняется или обновляется.
Следующий файл с той же нормализованной структурой заголовков получает эту схему
как предварительное предложение. Публикация всё равно требует явного
подтверждения сопоставления и строк.

### Технический английский

Машиночитаемый словарь размещается в:

```text
src/apps/imports/domain_glossary.py
```

Человекочитаемая политика и базовые соответствия размещаются в:

```text
docs/domain/technical-english-glossary.md
```

Новые доменные имена сначала добавляются в контролируемый словарь, затем
используются в моделях и сервисах.

## Безопасность данных

Patch 011.4 не содержит реальных ФИО, производственных документов, оперативной
истории, сетевых параметров или конфиденциальных сведений. Он только создаёт
контролируемые профили для последующего локального импорта.

Профиль `local-validation` явно запрещает обычный экспорт. Безопасный
презентационный профиль не допускает реальные персональные данные.

## Совместимость

- существующие попытки импорта при миграции относятся к `presentation-safe`;
- существующие вызовы `create_import_batch` без явного профиля используют профиль
  по умолчанию;
- CSV/XLSX parser, staging, review и publication сохраняют прежний контракт;
- схема БД изменяется миграцией `imports.0004`;
- PostgreSQL-специфичные функции не используются.

## Проверки

Patch относится к высокому риску из-за новой миграции и изменения канонического
снимка публикации. Требуется профиль `FULL`:

- Ruff;
- `compileall`;
- Django checks;
- проверка и применение миграций с чистой БД;
- профильный gate Patch 011.4;
- тесты `apps.imports`;
- полный test discovery;
- локальный commit только после полного успеха.
