# ЭОД — открытые вопросы и отложенные задачи

## 1. Текущий блокер

Завершить DOCS-001:

- создать все канонические документы;
- мигрировать старые project state files;
- добавить PR template;
- добавить documentation contract gate;
- проверить ссылки и baseline consistency;
- провести пользовательскую приёмку документационного контура;
- зафиксировать последовательную журнальную стратегию, UX-001 и paper-first режим журнала ключей.

## 2. Обязательная ревизия после DOCS-001

PLAN-001 должен установить по каждому модулю:

- что фактически реализовано;
- что реализовано частично;
- что сделано иначе, чем планировалось;
- какие tests/gates реально актуальны;
- какие presentation scenarios работают;
- какие этапы утратили актуальность;
- какое направление и vertical slice выбрать следующим.

Результат PLAN-001 должен включать конкретный первый журнальный vertical slice, а не общий приказ «завершить все журналы».

## 3. Структурированные журналы

Требуют проверки и/или завершения:

- журнал заявок;
- журнал распоряжений;
- журнал дефектов оборудования;
- журнал ввода оборудования в работу;
- журнал РЗА и телемеханики;
- журнал учёта работ по нарядам;
- журнал учёта работ по распоряжениям.

Для каждой формы нужны source traceability, точные графы, специализированные rules, UI, минимальные реальные связи, presentation data, automated gates и acceptance scenario.

Рабочая стратегия: один журнал целиком → минимальные связи → приёмка → следующий журнал.

## 4. Журнал выдачи и возврата ключей

Текущая продуктовая позиция — paper-first:

- бумажный журнал остаётся основным рабочим оригиналом;
- полный электронный lifecycle выдачи/возврата не входит в обязательный внутренний прототип;
- возможный электронный справочник, контроль outstanding keys или зеркальная регистрация требуют отдельного предметного и UX-решения;
- демонстрационный сценарий не должен изображать бумажный процесс полностью электронным без реальной необходимости.

## 5. Наряды и распоряжения

Открытые предметные вопросы:

- электронный оригинал наряда;
- журнал учёта работ по нарядам и журнал работ по распоряжениям;
- целевые инструктажи;
- первичный и ежедневный допуск;
- изменения состава бригады;
- переводы;
- приостановка и возобновление;
- окончание, закрытие и хранение;
- доказательства действий и требования к подписям;
- бумажный, гибридный и электронный режимы.

Решение принимается после актуального нормативного исследования.

## 6. Эксплуатационные работы

Добавить отдельную модель и/или справочники для работ в порядке текущей эксплуатации:

- перечень для оперативного персонала;
- перечень для ремонтного персонала;
- связь с рабочим местом, оборудованием и инструкцией;
- период действия и редакция.

## 7. Переключения

Минимальный реестр ещё требует реализации или доказательной ревизии. Автоматическая генерация БП/ТБП/ТПП и safety engine остаются отдельной дальней очередью.

## 8. Оперативный журнал

Нужна отдельная ревизия текущего редактора и assistance:

- insertion caret в конец записи;
- Ctrl+Left/Right/Home/End внутри текущей записи;
- PgUp/PgDown без прокрутки всей страницы;
- редактирование автоматически вставленной semantic link;
- отсутствие дублирования link icon при copy/paste;
- отсутствие скачка страницы при клике вне листа;
- шаблоны, сокращения и автодополнение.

## 9. UX-001

Параллельный UI/UX-контур должен подготовить:

- evidence-based audit текущего UI;
- UI principles;
- application shell;
- design tokens;
- component contract;
- interaction contract;
- page archetypes;
- keyboard/focus/overlay rules;
- три reference screens;
- implementation roadmap без остановки продуктовой разработки.

Открытые риски:

- чрезмерно абстрактная дизайн-система без проверки на реальных экранах;
- повторное создание локальных компонентов в каждом журнале;
- перенос всех UI-решений в отдельный чат без интеграционного контроля;
- попытка заранее спроектировать все будущие экраны.

## 10. Импорт и данные

- шесть неоднозначных строк документации рабочего места остаются в staging;
- проверить полноту и терминологию импорта оборудования;
- поддерживать общий equipment family для ЩПТ/ШОТ;
- закрепить управляемый RU→EN domain lexicon;
- не импортировать реальные чувствительные данные в presentation profile.

## 11. Тесты и quality gates

- Django test command обнаруживает `0 test(s)`;
- определить минимальный обязательный smoke/integration suite перед крупными продуктовыми slices;
- нулевое число обнаруженных tests не считать доказательством регрессионной защиты;
- добавлять профильные tests/gates вместе с каждым журналом.

## 12. Инфраструктура

- проверить documentation CI после DOCS-001;
- формализовать post-merge preview update;
- определить retention backups;
- reverse proxy/HTTPS/domain не являются текущим блокером;
- production hardening относится к отдельному официальному этапу;
- не расширять инфраструктурный scope без подтверждённой продуктовой необходимости.

## 13. Документационная непрерывность

- применимые canonical docs обновляются в том же PR, что и изменение;
- после принятого patch/repair обязательны актуальные `CURRENT_STATE.md` и `CURRENT_HANDOFF.md`;
- новый accepted baseline фиксируется после post-merge verification;
- внезапное завершение чата не должно требовать восстановления состояния по памяти.

## 14. Известные противоречия старой документации

До merge DOCS-001 старые файлы могут утверждать:

- что основной процесс — локальный Python patch;
- что push всегда запрещён;
- что SQLite является основной runtime database;
- что следующий этап — INFRA-002;
- старые baseline SHA.

Эти утверждения должны быть удалены из канонического слоя или сохранены только как история.
