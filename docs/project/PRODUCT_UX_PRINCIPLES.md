# ЭОД — продуктовые и UX/UI-принципы

**Статус:** canonical / accepted  
**Дата принятия:** 29.07.2026  
**Основание:** исследование специализированных продуктов и вертикальных модулей, а также пользовательская приёмка UX-FOUNDATION-001.

## 1. Назначение

Этот документ определяет обязательные принципы продуктового проектирования, UX/UI и User Experience для всех модулей ЭОД.

Он не заменяет:

- нормативное исследование;
- утверждённые формы журналов и документов;
- предметные lifecycle;
- профильные acceptance criteria.

Внешние продукты являются источниками доказательств и паттернов, но не автоматически утверждёнными требованиями ЭОД.

## 2. Статусы исследовательских решений

Для каждого внешнего паттерна используется одна из классификаций:

- `ADOPT` — принцип переносится почти напрямую;
- `ADAPT` — применяется после адаптации к ЭОД и российской предметной области;
- `REJECT` — сознательно не используется;
- `DEFER` — полезно, но не входит в текущий горизонт;
- `VERIFY` — доказательств недостаточно или требуется нормативная/предметная проверка.

Дополнительно всегда разделяются:

```text
внешний факт
→ аналитический вывод
→ предлагаемое решение ЭОД
→ статус утверждения
```

Маркетинговое заявление поставщика не считается доказательством полноты runtime-реализации.

## 3. Best-of-breed critical path

ЭОД конкурирует одновременно с:

1. бумажным журналом или бланком;
2. Excel/Access/Word-процессом;
3. узкой специализированной программой;
4. крупной корпоративной платформой.

Преимущество «всё в одной системе» не оправдывает неудобный ежедневный сценарий.

Перед реализацией каждого основного модуля определяется один главный пользовательский маршрут. Он сравнивается с фактическим рабочим процессом и лучшим доступным узким референсом по:

- времени выполнения;
- количеству обязательных действий;
- объёму повторного ввода;
- объёму ручного текста;
- вероятности ошибки;
- качеству печатного результата;
- восстановлению после прерывания;
- клавиатурной и мобильной работе, если они значимы.

Требование означает паритет критического маршрута, а не копирование всего специализированного продукта.

## 4. Общие продуктовые принципы

### 4.1. Один первичный объект — несколько представлений

```text
первичный документ или факт
→ реестр
→ журнал учёта
→ рапорт
→ отчёт
```

Производные журналы и отчёты не становятся второй независимой базой и не требуют повторного ручного ввода.

### 4.2. Authoring и lifecycle разделяются

Быстро подготовить корректный документ и полностью провести юридически значимый электронный lifecycle — разные задачи.

Для нарядов и других сложных документов отдельно проектируются:

```text
authoring:
справочники → шаблон/копирование → проверка → предпросмотр → печать

lifecycle:
создание → согласование → действия участников → завершение → хранение
```

Полный lifecycle не добавляется без нормативного и предметного решения.

### 4.3. Общие механизмы не означают универсальную предметную карточку

Переиспользуются:

- идентификация;
- участники и роли;
- оборудование;
- документы-основания;
- связи;
- аудит и история;
- вложения;
- поиск;
- печать;
- visual primitives.

Специализированными остаются:

- оперативный журнал;
- наряд;
- переключения;
- дефект;
- обход;
- выдача ключей;
- заземления;
- иные source-bound формы и lifecycle.

### 4.4. Передача смены — отдельный workflow

Рапорт, активные документы, незавершённые действия, сдающий и принимающий не сводятся к последней текстовой записи оперативного журнала.

### 4.5. Обход — самостоятельная сущность

```text
маршрут
→ контрольные точки
→ измерения и чек-листы
→ отклонение
→ дефект
→ при необходимости оперативная запись
```

Оперативная запись хранит результат или связь, а не все данные обхода.

### 4.6. SCADA — необязательная интеграция

ЭОД должна полноценно работать без конкретной SCADA/ОИК-платформы. Схема, телеметрия и автоматические события подключаются через отдельную будущую интеграционную границу.

### 4.7. История вместо тихой перезаписи

Опубликованные, зарегистрированные, подтверждённые или подписанные состояния не переписываются. Исправление, отмена, замена участника и изменение срока создают доказательную историю.

### 4.8. Ознакомление, инструктаж, знания и подпись различаются

Подтверждение прочтения не подменяет:

- инструктаж;
- проверку знаний;
- персонально предоставленное право;
- подпись документа;
- подтверждение конкретного действия.

## 5. Единый UX/UI contract

### 5.1. Основное правило

> Одинаковые по назначению элементы во всех журналах выглядят и работают одинаково. Различия допускаются только там, где они обусловлены предметной функцией.

Запрещено создавать отдельную визуальную систему для каждого модуля.

Запрещён путь:

```text
feature-a classes
→ копия feature-b classes
→ независимое развитие
→ расхождение интерфейсов
```

### 5.2. Общесистемные компоненты

Единый shared layer охватывает:

- application shell;
- sidebar и topbar;
- page header;
- рабочую ширину и базовую сетку;
- typography, spacing, radii, shadows и semantic colors;
- primary/secondary/tertiary/destructive buttons;
- icon buttons;
- поля, поиск, select и validation;
- tabs и segmented controls;
- cards и panels;
- status chips;
- alerts, notifications и empty states;
- таблицы и заголовки;
- hierarchy selectors;
- date/time pickers;
- dialogs, overlays и mobile bottom sheets;
- loading, saving, conflict и error states;
- responsive behavior.

### 5.3. Специализированные рабочие области

Внутри общего shell сохраняют собственную предметную геометрию:

- трёхграфная форма оперативного журнала;
- лист, страница и разворот;
- ribbon и editor;
- нормативные отметки;
- наряд и его печатная форма;
- программа/бланк переключений;
- lifecycle дефекта;
- маршрут обхода;
- другие утверждённые source-bound формы.

Специализация не является разрешением менять общий внешний вид кнопок, полей, статусов и служебных панелей.

### 5.4. Обязательная cross-screen проверка

При добавлении или изменении shared-компонента сравниваются минимум:

- главная страница;
- reference structured journal;
- реестр оперативных журналов;
- зарегистрированный оперативный журнал;
- рабочая область смены;
- новый затрагиваемый модуль.

Проверяются одинаковые viewport, масштаб, длинные русские значения и состояния:

- normal;
- hover/focus;
- selected/current;
- disabled;
- loading/saving;
- validation error;
- empty;
- mobile.

### 5.5. User Experience важнее декоративного единообразия

Для критического сценария проверяются:

- понятность следующего действия;
- отсутствие ложных доступных действий;
- минимизация повторного ввода;
- сохранение контекста и позиции;
- предсказуемая клавиатура;
- отсутствие неожиданных page jumps;
- читаемость на рабочем мониторе и телефоне;
- понятное различие черновика, зарегистрированного состояния и истории;
- честная терминология без обещания несуществующего lifecycle.

## 6. Принятый визуальный baseline

```text
Direction A — спокойное светлое документно-операционное направление
```

Приняты:

- светлая нейтральная основа;
- спокойный синий акцент;
- высокая рабочая плотность;
- компактная служебная иерархия;
- понятная постоянная навигация;
- светлые status chips с отдельной цветной меткой;
- operator-first, а не admin-panel характер;
- адаптивные карточки и mobile patterns.

Direction A является общесистемным языком, а не стилем только журнала дефектов.

## 7. Применение к текущему roadmap

### Текущий OPJ-UX-001

Входит:

- shared Direction A layer;
- выравнивание одинаковых элементов;
- специализированный workspace оперативного журнала;
- зарегистрированные записи и рабочий черновик;
- существующие semantic references;
- responsive UX.

Не входит:

- регистрация черновика;
- handover lifecycle;
- templates/abbreviations/suggestions;
- автоматические события;
- action management;
- offline;
- SCADA;
- новые модели.

### Будущие отдельные work items

- `OPJ-LIFECYCLE-001`;
- `OPJ-ASSISTANCE-001`;
- `SHIFT-HANDOVER-001`;
- `PRODUCT-D2`;
- `PRODUCT-D3`;
- `PERMIT-AUTHORING-001`;
- `PERMIT-LIFECYCLE-001`;
- `SWITCHING-DOCUMENTS-001`;
- `CROSS-DOCUMENT-ACTIONS-001`;
- `ROUNDS-001`;
- `RZA-TM-RESEARCH`;
- `OFFLINE-001`.

Очередность уточняется сквозными демонстрационными сценариями и фактической готовностью модулей.

## 8. Приёмка нового модуля

Новый модуль не считается UX-ready, пока не доказано:

1. критический маршрут выполняется без лишнего повторного ввода;
2. общие элементы используют shared contract;
3. специализированные различия имеют предметное объяснение;
4. desktop и mobile читаемы;
5. keyboard/focus behavior не деградировал;
6. печатная форма сохранена, если она является рабочим результатом;
7. нет ложных lifecycle-действий;
8. сравнение с reference screens не выявило отдельную UI-систему.
