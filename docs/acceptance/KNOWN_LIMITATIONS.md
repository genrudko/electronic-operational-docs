# ЭОД — известные ограничения

Документ фиксирует ограничения честно и не позволяет демонстрационному прототипу выглядеть промышленной системой.

## Статус продукта

- независимый личный прототип;
- не является системой работодателя;
- не прошёл официальную информационную, нормативную и эксплуатационную приёмку;
- не предназначен для реальных оперативных записей;
- не отменяет бумажную документацию.

## Данные

- presentation profile использует вымышленные данные;
- фактическая матрица прав и оперативное распределение не воспроизводятся;
- реальные инструкции и приложения не хранятся в репозитории;
- часть форм пока описана источником, но точный состав граф может требовать дополнительной сверки;
- шесть неоднозначных строк документации рабочего места остаются в staging.

## Структурированные журналы

- общее ядро реализовано, но не все профильные журналы подтверждены завершёнными;
- source-bound catalog не означает готовность всех lifecycle rules;
- журнал ключей и журнал работ требуют точных источников и/или завершения;
- cross-document timeline реализован не полностью.

## Оперативный журнал

- assistance, templates, abbreviations and keyboard UX требуют отдельной ревизии;
- известные риски включают caret/navigation/scroll and semantic link editing;
- текущая реализация должна быть проверена через regression scenarios до объявления готовности внутреннего прототипа.

## Наряды и распоряжения

- полный lifecycle не подтверждён;
- нормативная допустимость полностью электронного режима не установлена;
- демонстрационное password confirmation/hash не является УКЭП или УНЭП;
- роли, инструктажи, допуски, переводы, изменения бригады, окончание и хранение требуют доказательной матрицы;
- режимы paper/hybrid/electronic должны маркироваться явно.

## Переключения

- минимальный реестр не равен генератору переключений;
- автоматическая генерация БП/ТБП/ТПП не входит в текущий принятый scope;
- топологический расчёт, interlocks, safety validation and RPA logic отсутствуют или не подтверждены;
- прототип не выдаёт команды реальному оборудованию.

## Подписи и целостность

- SHA-256 and canonical snapshot выявляют несогласованность данных;
- без внешнего trusted key механизм не защищает от администратора БД, способного изменить данные и пересчитать hash;
- юридическая значимость не заявляется.

## Инфраструктура

- VPS development and preview являются демонстрационными isolated contours;
- публичный domain, reverse proxy and HTTPS не настроены как production service;
- HA, replication, production monitoring and enterprise backup policy отсутствуют;
- доступ выполняется через SSH tunnel;
- VPS deploy key read-only, что сознательно исключает commits from server.

## Совместимость

- PostgreSQL является фактической VPS-СУБД;
- отдельные старые local scripts/docs могут всё ещё упоминать SQLite или Windows-centric workflow до полного cleanup;
- differences SQLite/PostgreSQL требуют targeted tests для Unicode, locking and transactions;
- mobile browser UX не считается полностью принятой только по проверке на ПК.

## Документация

- DOCS-001 создаёт новый канонический слой;
- до его merge active `main` содержит устаревшие инструкции;
- master plan после DOCS-001 ещё должен пройти PLAN-001 revision;
- статус модулей в `MODULE_MAP.md` предварительный до evidence audit.

## Ограничения при демонстрации

При показе обязательно сообщать:

1. это прототип;
2. данные демонстрационные;
3. paperless legality не заявляется;
4. switching automation отсутствует;
5. production security/integration не реализованы;
6. цель показа — подтвердить workflow and architecture feasibility.

## Изменение документа

Ограничение удаляется только после:

- реализации;
- automated gates;
- предметной/визуальной приёмки;
- обновления release notes and acceptance history.
