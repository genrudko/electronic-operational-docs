# ЭОД — приёмка внутреннего прототипа

## 1. Цель

Подтвердить не наличие отдельных экранов, а работоспособность цельного безопасного демонстрационного контура оперативной документации.

## 2. Обязательные области

- начало смены и текущее состояние документации;
- оперативный журнал;
- оборудование и персонал;
- дефекты;
- заявки и распоряжения;
- работы по нарядам/распоряжениям в утверждённом демонстрационном объёме;
- выдача и возврат ключей;
- документы переключений без автоматической генерации БП/ТБП/ТПП;
- передача смены;
- связи между объектами, записями, людьми и документами.

## 3. Условия среды

- accepted preview или exact development head известен;
- database identity подтверждена;
- presentation data reset воспроизводим;
- demo accounts работают;
- health and HTTP gates пройдены;
- пользователь открывает приложение через SSH tunnel;
- реальные персональные/оперативные данные отсутствуют.

## 4. Общие критерии готовности

### Функциональность

- пользователь проходит сценарий без admin и ручного исправления БД;
- обязательные поля, states and transitions соответствуют source-bound форме;
- записи связываются с правильным оборудованием, участниками и документами;
- история и audit сохраняют исходное событие;
- поиск and filters возвращают ожидаемые данные;
- validation errors понятны и не уничтожают введённые данные.

### Предметная корректность

- terminology соответствует оперативной практике;
- управление/ведение, роли и виды документов не смешиваются;
- электронное подтверждение не называется юридической ЭП;
- бумажный/гибридный/электронный режим указан честно;
- формы не восстанавливаются по памяти при наличии source document.

### UX

- интерфейс только русский;
- основной сценарий не показывает system codes/hashes;
- формы читаемы при обычной плотности;
- keyboard behavior не ломает ввод оперативной записи;
- выбор оборудования и персонала масштабируется;
- нет blocking scroll/focus/link defects;
- critical actions имеют понятное подтверждение.

### Надёжность

- page refresh не теряет saved state;
- повторное действие не создаёт неочевидные duplicates;
- migrations and reset воспроизводимы;
- preview and development isolated;
- regression checklist проходит.

## 5. Блокирующие дефекты

Прототип не принимается при:

- потере/перезаписи зарегистрированной истории;
- возможности работать по technical schema как по утверждённой форме;
- неправильной database/organization isolation;
- невозможности завершить один из обязательных сценариев;
- неверной роли участника или разрешении запрещённого перехода;
- потере semantic links/equipment relation;
- UI defect, делающем ввод оперативной записи ненадёжным;
- использовании реальных чувствительных данных;
- failure presentation reset;
- недоступности accepted preview.

## 6. Неблокирующие ограничения

Могут быть приняты с follow-up:

- косметические различия вне critical route;
- неполный advanced filtering;
- отсутствие позднего export format;
- отсутствие автоматической генерации switching documents;
- функции дальней очереди, явно указанные как out-of-scope.

Они фиксируются в `KNOWN_LIMITATIONS.md` и `OPEN_ITEMS.md`.

## 7. Evidence

Для приёмки сохраняются summary:

- exact branch/head;
- reset/data state;
- account/role;
- пройденные scenarios;
- screenshots/video при необходимости;
- найденные defects;
- результат repair;
- final user decision.

Чувствительное видео/архив не коммитится в Git.

## 8. Решение

- `accepted`;
- `accepted with follow-up`;
- `repair required`;
- `rejected`.

Принятие внутреннего прототипа не означает промышленную или нормативную приёмку системы предприятия.
