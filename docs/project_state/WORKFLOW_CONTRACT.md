# ЭОД — обязательный workflow разработки

## 1. Роли

Пользователь — эксперт предметной области энергетики и не обязан редактировать код.
Ассистент самостоятельно проектирует изменения и выдаёт один полный автономный Python-скрипт.

## 2. Двухфазная непрерывность контекста

### Перед каждым Patch/Repair

Обязателен свежий pre-patch snapshot:

```text
EOD_PREPATCH_SNAPSHOT_CURRENT.zip
```

Патч не создаётся до проверки branch, HEAD, clean worktree, manifest и самосогласованного SHA-256.

### После каждого визуально принятого Patch/Repair

Полностью пересобирается:

```text
EOD_CURRENT_CONTEXT.zip
```

Пакет отражает последний визуально принятый baseline. Технически успешный, но ещё не принятый
commit не заменяет последний accepted package.

В корне пакета всегда находятся:

```text
README_FIRST.md
START_NEW_CHAT.txt
CHAT_HANDOFF.md
snapshot_manifest.json
```

## 3. Автономный patch

Каждый patch обязан:

1. создать файловый лог до запуска preflight;
2. проверить точную ветку, HEAD и чистый worktree;
3. проверить snapshot предстоящего patch по marker, sidecar SHA-256 и внутреннему manifest;
4. проверить baseline-хеши;
5. декодировать весь payload, проверить SHA-256, LF и ровно один завершающий перевод строки;
6. получить эксклюзивный доступ к обеим SQLite;
7. создать резервные копии файлов и БД;
8. применить полный payload без ручных правок;
9. выполнить Ruff и `compileall`;
10. выполнить Django check для presentation и development;
11. проверить генерацию миграций;
12. мигрировать чистую и обе рабочие БД;
13. выполнить профильные gate;
14. выполнить профильные и полные тесты;
15. проверить точный список изменённых файлов;
16. создать локальный commit только после полного успеха;
17. не выполнять `git push`;
18. выполнить полный rollback при любой ошибке до подтверждённого commit.

## 4. Приёмка

Технический успех не равен окончательной приёмке. После запуска проверяются реальные маршруты,
формы, сценарии, данные и блокирующие UX-дефекты. Accepted package обновляется только после
явного решения основного интеграционного чата.

## 5. Источники истины

1. Git bundle и snapshot manifest.
2. `CURRENT_STATE.md`.
3. миграции и профильная диагностика;
4. patch-логи;
5. `PATCH_HISTORY.md` и `DECISION_LOG.md`;
6. сообщения чата;
7. исторические планы.

## 6. Ограничения

- реальные персональные и производственные данные не коммитятся;
- SQLite остаётся локальной СУБД прототипа, PostgreSQL — целевой;
- проект не объявляется внедрённой системой предприятия;
- автоматический push запрещён;
- отмена бумажного дублирования не предполагается без официального решения.
