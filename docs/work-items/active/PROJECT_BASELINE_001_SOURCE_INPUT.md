Пакет построен на четырёх слоях:

# Утверждённые решения для будущего baseline

**Статус:** `USER-ACCEPTED / MUST PRESERVE`
**Дата фиксации пакета:** 30.07.2026

## 1. Управление проектом

1. План, checklist, module contracts, acceptance criteria и отчёты пишутся **на русском языке**.
2. Английский сохраняется для технических идентификаторов, путей, моделей, функций, branch names и work item IDs.
3. Разработка строится строго:

```text
релиз
→ модуль
→ capability / подмодуль
→ work item
→ patch / repair
```

4. Новый work item не стартует без exact baseline, источников, UX-контракта, scope, out-of-scope, acceptance criteria и разрешённых файлов.
5. Верхнеуровневый план не изменяется внутри обычного feature PR.
6. Нужен единый глобальный checklist: готово / в работе / заблокировано / осталось.
7. Проценты готовности не используются как основной показатель; готовность определяется принятыми capabilities и acceptance criteria.
8. GitHub остаётся источником истины; активные application changes не вносятся в `main` напрямую.

## 2. Статус референсного перечня

Документ, происходящий из перечня документации рабочего места оперативного персонала Кочубеевской ВЭС, далее называется:

> **Референсный перечень оперативной документации**

Его происхождение сохраняется для traceability, но он используется:

- как coverage-source;
- как источник классов документов, журналов, инструкций, схем, программ, списков и графиков;
- не как обязательная конфигурация одного объекта;
- не как нормативно исчерпывающий отраслевой перечень;
- не как автоматическое доказательство допустимости электронной формы.

## 3. Презентационный релиз

`DEMO-RELEASE` — не минимальный MVP. Он должен показать компании целостный образ реализуемой ЭОД и охватить основные процессы, но сложная промышленная/инженерная глубина может быть перенесена в post-demo.

Окончательный состав Demo/Post-demo должен быть выведен из coverage-аудита, а не из памяти.

## 4. Электронные, гибридные и бумажные контуры

### Обязательно для Demo

- нормативная модель электронных и гибридных документов;
- модель простой электронной подписи (ПЭП), идентификации, повторной аутентификации, целостности и аудита;
- различение подписи, ознакомления, инструктажа, проверки знаний и подтверждения действия;
- доказуемость авторства, времени и неизменности зарегистрированных состояний.

### Наряды и распоряжения

- сам **наряд-допуск** — гибридный: электронное authoring/сопровождение + бумажный оригинал и обязательные бумажные подписи там, где от них нельзя отказаться;
- **журнал учёта работ по нарядам** — электронный первичный журнал;
- **журнал учёта работ по распоряжениям** — бумажный оригинал с электронным дублированием сведений;
- **журнал распоряжений** — бумажный оригинал с электронным дублированием сведений;
- электронная копия бумажного журнала не должна ошибочно называться юридически значимым электронным оригиналом.

## 5. Отдельные продуктовые решения

### Включить в Demo

- оперативный журнал;
- журнал дефектов;
- заземления как отдельные инвентарные объекты и операции установки/снятия, связанные с ОЖ и передачей смены;
- «людской» модуль: организации, персонал, квалификации, предоставленные права, область и срок действия права;
- работы в порядке текущей эксплуатации как отдельный контур;
- хранение, версии и актуальность утверждённых/оперативных схем как документации;
- конкурентный benchmark и точечные референсы для каждого work item;
- единый Direction A UX/UI contract.

### Работы в порядке текущей эксплуатации

Разделить:

- для оперативного персонала — график эксплуатационных работ;
- для ремонтного персонала — утверждённый перечень работ, выполняемых в порядке текущей эксплуатации;
- конкретный факт выполнения и журнал эксплуатационных работ.

### Схемы

В Demo:

- реестр;
- тип;
- объект применения;
- действующая редакция;
- версии;
- утверждение/актуальность;
- просмотр и печать;
- связи с оборудованием и документами.

Post-demo:

- редактор схем;
- интерактивная электрическая модель;
- topology/state/interlock engine;
- интеграция с переключениями.

### Явно Post-demo

- электронный журнал выдачи/возврата ключей; текущая модель остаётся paper-first;
- специализированный проект БП/ТБП/программ переключений и инженерная автоматизация переключений;
- автоматическая генерация последовательностей;
- SCADA как обязательная основа;
- полноценный offline-first;
- промышленная HA/репликация;
- внешние корпоративные интеграции без отдельного work item.

## 6. Конкурентные продукты

Для каждого основного модуля обязательны:

```text
критический сценарий
→ бумага / Excel / Word
→ узкий специализированный продукт
→ комплексная платформа
→ решение ADOPT / ADAPT / REJECT / DEFER / VERIFY
→ измеримые acceptance criteria ЭОД
```

Общий рыночный поиск уже выполнен. Перед work item допускается только точечное исследование 2–4 релевантных референсов.

## 7. UX/UI

- Direction A — общесистемный язык.
- Нельзя создавать независимую дизайн-систему на каждый журнал.
- Одинаковые по назначению элементы должны совпадать визуально и поведенчески.
- Специализированный workspace не меняет общий shell и shared primitives.
- Desktop и mobile проверяются по реальным маршрутам.
- Ложные кнопки, несуществующий lifecycle и технический admin-panel UX запрещены.
